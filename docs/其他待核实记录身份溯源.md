# 一码归一码历史群记录身份溯源

日期：2026-10-23。目标：线上business_events.id=1806，callback_id=1821。只记录脱敏结构、相等性和类型，不复制个人标识、姓名、群ID、头像URL、凭据或回调密文。

## 证据链

1. 解密收件箱JSON：Event=change_external_chat、ChangeType=update、UpdateDetail=del_member、QuitScene=0、MemChangeCnt=1，CreateTime=1792661453。它报告主动退出1人，不直接说明该成员类型。
2. payload包含MemChangeList、LastMemVer、CurMemVer。但MemChangeList已被保存为[{}]，未保留成员ID。
3. 业务记录的_before_members包含当前member_candidates中同一个成员ID，其原始type字段为1；member_candidates.member_type也为1。因此内部成员分类来自离群前群快照字段，不是头像补全时将type=2改为1。
4. _all_member_candidates同样为type=1，现行分类按内部成员保留group_change_unknown，不计入外部客户流失。此前迁移的_classification_original用于保留原行，现行冻结迁移没有按昵称做身份合并。
5. 对比同主体有真实媒体的customer Profile：成员ID不相等；昵称相等，但两侧没有可用的非空unionid关联。此前员工接口按目标成员ID读取返回60111，不能以此证明该ID就是有照片的客户ID。
6. 检查11份现存avatar/deploy数据库备份：目标记录的候选类型和_before_members中的类型均为1，回调成员列表均已是空字典列表。没有发现备份保留了足以恢复成员ID的内容。

这些只能说明“为何本地记成内部成员”，不能证明原始平台回调一定指向这位内部成员；系统比对依据仍是inferred。群快照是否存在时序偏差，也不能仅凭昵称排除。现有证据不足以把两条不同ID的身份合并。

## 发现并修复的解析缺陷

app/security.py旧parse_xml将所有嵌套列表元素按子字段字典解析；对于MemChangeList/Item的CDATA文本，Item没有子元素，于是变成{}，丢掉成员ID。收件箱只加密保存解析后的JSON，不保存原始XML，所以无法从该密文中恢复已经丢弃的CDATA。

修复：仅对MemChangeList的文本Item保留原字符串；其他原有结构化字段保持兼容。新增回调ID与快照差异的核对：有完整文本成员ID时，必须与差异成员集合、数量、唯一性一致；冲突保留callback_snapshot_conflict和待核实，不按昵称关联。旧[{}]没有被伪造成有效ID，也没有重放旧历史记录。

此次不修改1806的成员ID、分类、人数、识别依据或头像。若将来取得原始回调XML、可验证的跨ID映射或对应历史API响应，可再次审查；仅管理员口头确认同名、相同照片或昵称不足以自动合并账户。
