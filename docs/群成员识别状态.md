# 客户事件分类与识别依据

代码核对日期：2026-10-24，源码基线 `24e6586`。依据 `app/worker.py`、`app/event_classification.py`、`frontend/src/groupEvidence.ts` 及冻结迁移逻辑。真实样本与待验范围见 [真实钉钉环境验收记录](真实钉钉环境验收记录.md)，本轮未重新调用平台。

业务分类和证据来源分别记录。外部客户的新增、删除、主动退群、被移出群进入对应入口，列表人数、总览卡片、趋势和排行使用同一分类。快照比对是识别依据，不再是把外部客户排除出业务列表的理由。

## 四类业务事件

| 条件 | 业务分类 | 统计方式 |
| --- | --- | --- |
| add_external_contact，含员工和外部客户 ID | 新增联系人 | 计入新增；姓名缺失保留 ID 并补全资料 |
| del_external_contact | 删除联系人（员工删除客户） | 计入删除 |
| del_follow_user | 删除联系人（客户删除员工） | 计入删除 |
| 群退出原因是主动退出，识别成员为外部联系人 | 主动退群 | 计入外部客户退群 |
| 群退出原因是被移出，识别成员为外部联系人 | 被移出群 | 计入外部客户被移出 |

群内成员的 `member_type=2` 表示外部联系人；这与客户资料中的微信/企微类型是不同字段。姓名、头像或操作人缺失不改变已经具备证据的业务分类。群主不会被当作操作人。

## 快照识别的判断依据

当前处理链路依据平台报告的原因及人数，再用事件前后成员列表关联人员。只有原始候选数与回调人数一致、成员有 ID 或历史有效姓名、成员 ID 不重复，并且已标记为有效快照差异时才采用。生成差异时还要求事件前基准有效，期间没有新增成员。保存 ID 的记录即使姓名未补全，也能按外部成员类型归类。

事件前基准的采集时间必须不晚于回调发生时间；重试沿用该事件首次保存的基准，不用后来读到的成员列表替换。XML 中 `MemChangeList/Item` 为文本时保留成员 ID；只有完整文本列表才参与额外核对，其数量、唯一性和成员集合必须与快照差异一致，否则标记 `callback_snapshot_conflict` 并留待核实。旧解析器保存的 `[{}]` 不视为有效 ID，也不能仅凭回调 ID 列表跳过事前快照判定。历史姓名兼容只用于已有证据快照，不按同名重新配对身份。

群详情请求使用持久化的 `capture_version` 区分先后顺序，旧请求的详情及头像补全结果不能覆盖后发请求的快照。该版本与 `synced_at` 分离：后者仍为详情响应完成时间，请求开始时间不作为事件前快照证据。新请求失败时保留已有完成快照；原有证据规则与 inferred 分类不变。同群多个回调的完整处理串行化仍不属于本次修复范围。

匹配通过的外部客户保留 `resolution=inferred`，与直接明确身份的 `exact` 区分，但两者都按业务分类进入客户列表和统计。详情在“识别依据”中保留系统推断说明。这代表采用有证据的关联结果，不代表平台逐人确认；同一时段复杂并发变化仍可能影响快照推断。

## 为什么仍有“其他 / 待核实”

| 原因 | 判断依据 | 后续处理 |
| --- | --- | --- |
| 企业内部员工 | 快照成员类型为 1 | 保留记录，不计入外部客户流失 |
| 成员类型未知 | 有人员关联，但不能确定是客户还是员工 | 补充类型前不计入客户人数 |
| 身份无法关联 | 缺少事件前快照、取群接口失败、差异人数不一致、存在并发加入、候选无有效身份或重复 ID、回调成员 ID 与快照冲突 | 明确展示原因；可恢复的接口失败通过任务重试处理 |
| 退出原因未知 | 不属于已知主动退出/被移出原因 | 不猜测业务动作 |

旧实现把所有快照识别结果都留在待核实，是为了避免把内部员工或并发变化算成客户流失，但范围过宽。本次改为只保留上表这些情况，证据充分的外部客户正常归类。

## 同一次变更的混合成员

例如平台报告 3 人被移出，比对出 2 名外部客户和 1 名内部员工：客户页显示 2 人，其他页显示 1 人。记录保留 `reported_quantity=3` 说明原始报告人数；本行 `quantity` 分别为 2、1，合计仍为 3。事件使用稳定的 `group`、`group_other` 键，重试更新原记录，不重复累计。如果后续补全使剩余分组不再需要，删除该回调旧的剩余分组。

## 历史记录升级

`alembic upgrade head` 的 `0002_customer_groups` 数据迁移按相同证据重新分类历史 `group_change_unknown` 主记录：外部客户进入对应入口，内部/未知部分保留，原主记录 ID 不变。旧版只有有效姓名和成员类型的匹配快照也支持；没有保存身份或快照证据的记录不会凭现在的群列表补造。迁移分批处理，重复升级不增加记录，记录迁移前数据供降级恢复；迁移逻辑及表定义已冻结，避免后续应用改动影响旧库升级。

本地同步脚本在备份后自动执行迁移，无需手工删除数据或重放回调。仅上传前端不会完成历史归类；完整部署必须更新后端并迁移数据库。
